# Home & Widgets Data Contracts

This document defines the data contracts for DormWay Home/feed widget system, including API endpoints, data structures, and integration rules.

## Scope

**In scope:**
- Feed cards from `/api/v2/students/me/feed`
- Campus/home widget payload paths for city/campus/weather data
- Contract rules for reveal behavior and metadata required by clients

**Out of scope:**
- Prompt authoring strategy details
- WidgetKit extension UI specifics
- Visual design specifications

## Web Rendering Integration

Widget contracts are consumed through LockedIn web rendering boundaries with specific constraints:

- Widget contract changes must remain compatible with server-first page composition plus client widget islands
- New widget data access paths should avoid forcing route-level `'use client'` at page/layout boundaries unless interaction requires it
- Contract updates that increase hydration/runtime cost should include explicit tradeoff notes

## API Contracts

### Feed Endpoint

```
GET /api/v2/students/me/feed?limit=<n>
```

#### Card Structure

All feed cards follow this contract-stable shape:

**Required core fields:**
- `id` - Unique card identifier
- `type` - Card type identifier
- `category` - Card category
- `label` - Display label
- `title` - Card title
- `subtitle` - Card subtitle
- `basePriority` - Base priority score
- `computedScore` - Computed relevance score

**Reveal fields:**
- `hasReveal` - Boolean indicating if card is expandable
- `revealText` - Text for reveal action (when hasReveal is true)
- `revealContent` - Additional content shown when expanded

**Metadata:**
- Metadata object is additive and type-specific
- Clients should ignore unknown keys to maintain forward compatibility

## Reveal Contract Rules

The reveal system follows strict consistency rules:

### Default Rule
- If `hasReveal = false`, `revealText` should be omitted
- If `hasReveal = true`, `revealContent` must be non-empty and `revealText` must be present

### Card-Specific Exception (day_conditions)
- `revealContent` may be present even when `hasReveal = false` to preserve structured body parsing in iOS
- Content includes `Conditions`, `Planning`, and `Be Prepared` sections
- Clients must treat `hasReveal` as the source of truth for expandability, not `revealContent` presence

## Card Type Behaviors

### Traffic Alert Cards (`traffic_alert`)
- Low-signal weather advisories are suppressed
- Alerts are generated, filtered, scored, then capped (filtering occurs before slicing)
- Severe closures/incidents outrank low-signal advisories

### Mobility Insight Cards (`mobility_insight`)
- Placeholder/empty cost comparisons are removed
- Reveal content includes only meaningful alternatives

### Day Conditions Cards (`day_conditions`)
- Structured `revealContent` sections are preserved for iOS body parsing compatibility
- `hasReveal` is only enabled for meaningful extra detail (truncated subtitle, actionable planning, or non-generic prep items)
- Generic planning/prep boilerplate is filtered out before render
- Examples of filtered content: "next 24 hours", "warm clothing", "check transit delays"
- Output maintains stable metadata keys used by iOS scoring/chips

## Runtime Dependencies

### Prompt Management
Feed card quality depends on database-managed prompt versions stored in `llm_prompts` table.

### Environment Configuration
- `PORTKEY_VIRTUAL_KEY_PERPLEXITY` must be set for Perplexity model calls
- Runtime city/weather/news prompt updates are versioned in database
- Apply prompt changes via migration/scripts, not ad-hoc inline edits

## Change Policy

Before modifying card data contracts:

1. **Validate active code path** - Confirm changes target V2 endpoint path
2. **Check client compatibility** - Confirm iOS/client parser expectations for affected card type
3. **Preserve existing keys** - Prefer additive metadata over breaking changes
4. **Update documentation** - Update this SoT and related prompt documentation in same PR
5. **Check rendering boundaries** - If web rendering/data-boundary assumptions change, update web rendering documentation

<Warning>
Contract changes should maintain backward compatibility. Clients may not immediately update to handle new fields or modified structures.
</Warning>
