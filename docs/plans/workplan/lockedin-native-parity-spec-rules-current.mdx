# LockedIn Native Parity Spec Rules (Current)

## Decision Framework
For every parity decision:
1. Determine whether this is a product rule or a UI preference.
2. If product rule: native must match web outcomes.
3. If UI preference: native may diverge when platform usability is better.
4. Any divergence must be documented with user-facing equivalence.

## Must Follow Exactly
### IA and destination semantics
- Top-level destination meaning must remain consistent across platforms.

### Workflow semantics
- Task lifecycle semantics.
- Scheduling semantics.
- Settings semantics and side effects.

### Data and edge-case semantics
- Empty/loading/error behavior.
- Filter/sort outcomes.
- Permission and fallback semantics.

### Shortcut/intent contracts
- Deep-link/intent destination outcomes.
- Keyboard shortcut outcome mapping parity.

## Should Intentionally Diverge
### Layout mechanics
- Do not force web layout-editor/grid authoring paradigms as the primary phone UX.

### Navigation chrome
- Do not mirror web sidebar patterns directly on native.
- Use native tab and split-view shells.

### Density and interaction targets
- Do not transplant desktop-density micro-controls to touch flows.

### Settings presentation hierarchy
- Grouping and entry points may differ if semantic parity is preserved.

## Surface-Specific Guardrails
### Today
- Match what appears and why it appears.
- Different arrangement controls are acceptable if users can achieve equivalent outcomes.

### Tasks
- Match planner/bulk/state semantics.
- Native gesture/sheet patterns may differ.

### Schedule
- Match event normalization and visibility semantics.
- Native alarms/live activity can be additive, not conflicting.

### Courses
- Match context transitions and intelligence semantics.
- Detail composition may differ by platform.

### Library
- Match pin/search/object lifecycle semantics.
- Native editor/file affordances may be richer.

### Settings
- Match value meaning, defaults, persistence, and side effects.
- Native placement may differ.

## Platform Quality Rules
### iPhone
1. Critical actions no more than two layers from tab root.
2. Prefer speed and low-friction workflows over panel depth.

### iPadOS
1. Split-view is primary.
2. Keyboard and pointer paths are first-class.

### Mac Catalyst
1. Keyboard-first flows must work.
2. Resize-safe layouts and pointer behavior must pass.

## Non-Negotiables
1. Web is source of truth for product behavior.
2. Native is source of truth for platform ergonomics.
3. Any behavior divergence must be explicit, justified, and test-covered.
