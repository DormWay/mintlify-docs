# DayPlan Today Screen — Decision Memo

Implementation direction for the current DayPlan Today screen (`feat/today-dayplan-v2`). References the spec at `SoT - DayPlan Today Screen` (last updated 2026-03-17), is governed by [Today Screen Product Principles (Current)](/docs/product/today-screen-product-principles-current), and should be read alongside the current web baseline in [LockedIn Web Today Page - Current Functionality (Current)](/docs/engineering/technical/lockedin/lockedin-web-today-page-current-functionality-current) and [LockedIn Web Today - Customization & Discoverability Memo (Current)](/docs/product/lockedin-web-today-customization-discoverability-memo-current).

---

## Product Thesis

The DayPlan Today screen is DormWay's primary iPhone surface. Its job is to answer "Am I okay — what do I need to deal with?" in under 10 seconds. It does this through honest orientation (GPS Hero: where you are in your day), clear urgency (what needs attention now), and a bounded timeline (your day, start to finish, with a visible end). It is not a dashboard, not a feed, and not a planning tool. It earns trust by being right about the things it shows, and by having a bottom.

---

## Keep

### GPS Hero (spec lines 78-93)
The 6-state adaptive hero is strong. "In class — FTVM 356", "Head to Baker Library", "Free until 2:30", "You're done for today" — these are the right opening lines for a student checking their phone. The state-priority cascade, stat pills, and course-colored treatment are well-designed.

**One required change:** see Clarify item #5 below (false confidence when "Free until X" coexists with due items).

### Smart Timeline (spec lines 97-137)
The chronological spine with past dimmed at 40%, future at full opacity, and a pulsing NOW marker with auto-scroll is a good spatial orientation model. Commitment cards with course colors, expandable detail, and "View Course" navigation are solid. Travel nudges, weather alerts, and conflict cards add real value without clutter.

**Keep as the day backbone,** but it should be secondary to attention items (see Top 3 Changes below).

### Stat Pills (spec line 58)
Classes count, due count, free hours, weather — compact, glanceable, honest. Good complement to the hero text. These stay.

### DueTodayBanner (spec line 103)
Red border, target icon, always first in timeline. This is the right urgency treatment. Keep it prominent.

### ComingUpSection (spec line 109)
Near-future assignment list at the bottom of the timeline. Lightweight look-ahead that prevents Sunday-night surprises. Keep.

### Real-Time Updates (spec lines 194-201)
Ably invalidation, scene-phase refetch, pull-to-refresh, 30-second timer for NOW marker. Sound real-time strategy. Keep.

### Analytics Events (spec lines 286-296)
Well-instrumented. Tracks hero state, timeline interactions, refresh behavior. Keep, but remove swipe-related events when the swipe stack is cut.

## Cut

### Swipe Card Stack (spec lines 140-163, files lines 223-226)

**Cut entirely.** The swipe stack is a discovery/engagement mechanic on a clarity/orientation screen. It violates Principle 3 (Finite and Calm) — a Tinder-style card stack at the bottom of "here's your day" invites browsing when the student's job is to check and leave. Known Issue #1 (spec line 270) confirms feed scoring produces only 2-3 surviving cards — a swipe stack with 2 cards feels broken.

**What to remove:**
- `SwipeStack/SwipeCardStack.swift`
- `SwipeStack/SwipeableCard.swift`
- `SwipeStack/SwipeCardDetailSheet.swift`
- `SwipeStack/StackIndicator.swift`
- Feed endpoint call (`GET /api/v2/students/me/feed?limit=10`) from the Today screen data sources
- Ably `feed.invalidate` handler for Today (spec line 196)
- Analytics events: `today_swipe_dismiss`, `today_swipe_save`, `today_card_tap` (spec lines 291-293)

**Implication:** This removes ~4 files and simplifies the data layer from 3 parallel requests to 2. The feed/discovery job can live on a separate tab if it proves valuable later.

### LLM Hero Subtitle (spec lines 166-190)

**Cut the Presentation Service integration for the hero subtitle.** The hero already has an adaptive state sentence + stat pills. A 30-token LLM-generated subtitle adds non-deterministic copy to the most important element on the screen. Different subtitle on each refresh erodes trust (Principle 6). The `summary.oneLiner` fallback is deterministic and sufficient.

**What to remove:**
- `POST /api/v2/students/me/summaries/batch` call from Today data sources
- `dayplan-gps-status` template usage (the template can remain in dormway-core for other uses)
- Subtitle swap logic in GPSHeroSection

**What to keep:** The `summary.oneLiner` from the DayPlan response as the subtitle. This is server-generated during DayPlan creation (not on-demand LLM), deterministic, and already exists.

**Implication:** This removes 1 network request on every screen load and eliminates the non-blocking async subtitle swap.

---

## Defer

### Suggested Study Blocks (spec line 108, file line 220)

**Defer — do not show in the initial ship.** Suggested blocks are AI-generated study time recommendations, which is the kind of prescriptive scheduling that DayPlan V2 was explicitly designed to avoid (SoT - DayPlan V2: "priority-first, not micromanaging scheduler"). Showing them with the same timeline placement as confirmed classes blurs the line between "things that are happening" and "things the AI thinks you should do."

**Implementation:** Keep `SuggestedBlockCard.swift` in the codebase but gate it behind a separate feature flag (not the main `HomeScreenMode.dayplan`). If future data shows students want study block suggestions, it can be enabled and tested independently.

**What stays in the data model:** `suggestedBlocks` remains in `DayPlanData` — it's already optional and won't affect decoding. The ViewModel simply doesn't include `suggestedBlock` items in the timeline array.

### Feed/Discovery Behavior on Today

**Deferred with the swipe stack cut.** If ambient discovery proves valuable, it should be a separate surface (its own tab, or integrated into the existing Cue/HeadsUp widget system on web). It does not belong on the Today screen.

### courseIntelligence / readingPrep Display

**Defer.** The data model includes `courseIntelligence` and `readingPrep` fields (spec lines 256-257) but the spec doesn't describe how they're rendered on Today. These are DayPlan V3 / Event Readiness Layer concepts (see `Event Readiness Layer - DayPlan V3 Spec (Draft).md`). Keep them in the data model; don't render them yet.

## Clarify Before Shipping

### 1. Task Interaction Model

**The problem:** DueTodayBanner shows "3 due today" with a red border, but there's no interaction beyond visibility. Students can't tap into assignment detail, mark something complete, or triage from Today. The current spec makes tasks read-only on the primary screen.

**What must be decided:**
- Does tapping the DueTodayBanner navigate somewhere? If so, where — a task detail view, the Tasks tab, or an inline expansion?
- Can students mark a task complete from Today? Even a lightweight "done" gesture would make the "due today" banner actionable rather than just stressful.
- How does this relate to the Tasks widget on the web Home V2? Should the interaction model be consistent?

**Recommendation:** At minimum, tapping the DueTodayBanner should expand to show the individual due items with tap-to-navigate to assignment detail. Inline completion (checkbox) is a strong follow-up but can ship later.

### 2. Empty and Edge States

**The problem:** The spec doesn't describe these states, which are common:
- **No classes today** (weekend, break, light schedule): What does the timeline show? Is the hero "You're done for today" at 8am? That feels wrong.
- **No data yet** (new user who just connected Canvas, data hasn't synced): What does the student see?
- **Partial data** (schedule imported but no assignments synced): Does the hero imply everything is clear when it only has half the picture?
- **Evening-to-tomorrow transition** (Known Issue #6, spec line 280): The hero still says "Free time" even when showing tomorrow's schedule.

**What must be decided:**
- What is the hero state when there are zero commitments for today? Probably a distinct state: "Nothing scheduled today" (not "You're done").
- How does the screen communicate data coverage confidence? ("Based on your Canvas and 3 syllabi" vs. naked "You're clear")
- What does the evening transition hero say? Probably "Tomorrow" with the day's first commitment.

### 3. iPad/Mac Adaptation Strategy

**The problem:** The spec is entirely iPhone (single-column ScrollView, 14 Swift files in `App/Views/Today/`). No mention of iPad or Mac. The existing web Home uses a 5-widget batch system (SoT - Home & Widgets). Building a fundamentally different architecture per platform creates maintenance burden and breaks mental model transfer.

**What must be decided:**
- Is DayPlan Today the direction for all platforms, or is it iOS-only while web keeps the widget system?
- If all platforms: what's the migration path for the web widget system?
- If iOS-only: how do the two architectures stay conceptually consistent?
- For iPad specifically: does Today use a two-column layout (hero+timeline left, tasks+courses right)?

**Recommendation:** Ship iPhone-first. Document explicitly that iPad/Mac adaptation is deferred. But the underlying data model and priority logic (GPSHeroState, timeline item ranking) should be designed platform-agnostically so it can power iPad and Mac surfaces later without a rewrite.

### 4. Relationship to Existing Widget Architecture

**The problem:** The web Home V2 has a canonical 5-widget set: Today, Schedule, Tasks, Courses, HeadsUp (SoT - Home & Widgets, Widget Contract Table). The iOS DayPlan Today fuses schedule, tasks (as banners), and nudges (as timeline cards) into a single view. These are architecturally different approaches to the same job.

**What must be decided:**
- Does the DayPlan Today eventually replace the widget-based home on all platforms?
- Or do widgets remain the web paradigm while iOS uses the fused timeline?
- How does the iOS "View Course" navigation from a commitment card relate to the web Courses widget?

**Recommendation:** The timeline is the default widget — tall, vertical, showing your day. On iPhone, the default layout is opinionated (Hero + attention items + timeline + coming up) and works without configuration. But the architecture should support customization: students who want to rearrange sections, resize the timeline, show/hide elements, or pin courses can do so. On iPad/Mac, widget-level arrangement (timeline alongside tasks, courses, etc.) is the right model — more screen space makes spatial customization genuinely valuable. The underlying data layer (DayPlan V2 API, widget batch API) serves both. See Principle 8: "The default must be great. Customization is available, never required."

### 5. "Free Until X" + Due Items = False Confidence

**The problem:** GPS Hero priority cascade (spec lines 82-89) puts temporal states (In Class, Head to Class, Free Until) above "Due Today" except when nothing else applies. A student who is "Free until 2:30" but has 3 assignments due by midnight sees "Free until 2:30" as the hero — which is factually true but creates a false sense of calm.

**What must be decided:**
- Should "Due Today" always be visible alongside temporal orientation? (e.g., "Free until 2:30 · 3 due today" as a compound hero)
- Or should "Due Today" interrupt the temporal state above a threshold? (e.g., if dueToday.count > 0, always show it)
- Or are the stat pills sufficient? (The "due" pill already shows the count)

**Recommendation:** Add a secondary urgency line to the hero when `dueToday` is non-empty and the primary state is temporal (Free, Done). Something like the stat pill's "3 due" count pulled up into the hero section as a visible secondary line, not buried in the pills. This preserves the temporal orientation while preventing the "I'm free and everything is fine" misread.

## Top 3 Changes for the Current Spec

In priority order:

### 1. Remove the Swipe Stack
Biggest single improvement to the screen. Removes 4 files, 1 data source, and an interaction pattern that contradicts the screen's purpose. The Today screen should end after the timeline.

### 2. Make the Hero Honest About Urgency
Modify the GPSHeroState logic so that when the primary state is temporal (Free, Done) and `dueToday` is non-empty, the urgency count is visibly surfaced in the hero section — not just in the stat pills. This is the highest trust-risk element on the screen.

### 3. Make DueTodayBanner Tappable
The most important items on the screen (things that are due) should be actionable, not just visible. At minimum: tap to expand and see individual items. Next step: tap an item to navigate to its detail.

## Implement Now vs. Save for Later

### Implement Now (Current Ship)
- GPS Hero with 6 states + compound urgency line
- Smart Timeline (commitments, nudges, conflicts, due banner, coming up)
- Stat pills
- Pull-to-refresh + real-time updates
- DueTodayBanner with tap-to-expand
- `summary.oneLiner` as hero subtitle (deterministic)
- Current analytics events (minus swipe events)

### Save for Later (Future Iterations)
- Swipe/feed discovery (separate surface, not Today)
- LLM-generated hero subtitles (re-evaluate if deterministic subtitles feel too static)
- Suggested study blocks (gate behind separate flag, test independently)
- iPad two-column layout
- Mac density adaptation
- "What changed since last check" indicators
- Inline task completion from Today
- courseIntelligence / readingPrep rendering
- Adaptive density based on day load (light day = minimal screen, heavy day = tighter layout)
- User preference learning (show me things earlier/later, surface this course more)

---

## Unresolved Questions Before Ship

1. **What does Saturday morning look like?** Zero-commitment state needs explicit design, not just the "Done" fallback.
2. **What does "just signed up, no data yet" look like?** First-run Today state must not feel empty or broken.
3. **Does the evening transition show tomorrow?** Known Issue #6 needs a decision: does the hero switch to "Tomorrow" after a threshold hour?
4. **How much of the student's obligations does DormWay actually see?** If Canvas is connected but syllabi aren't uploaded, should Today communicate partial coverage?
5. **Is 30 minutes the right "Head to Class" threshold?** A student 5 minutes away needs a different message than one 25 minutes away. Should this use actual walking time data (which exists in the schedule timeline contract per SoT - Home & Widgets)?
