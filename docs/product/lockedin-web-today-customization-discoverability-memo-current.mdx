# LockedIn Web Today - Customization & Discoverability Memo

## Purpose

This memo documents the current product reality of customization on the LockedIn web Today page and the main UX gap around discoverability.

Use this when:
- reviewing the current web Today experience
- deciding what to fix next in the widget architecture vs. the default layout
- explaining why the page can feel more static than it actually is
- prioritizing implementation work around edit mode, resize affordances, and widget value by size

For current implementation behavior, use:
- [LockedIn Web Today Page - Current Functionality (Current)](/docs/engineering/technical/lockedin/lockedin-web-today-page-current-functionality-current)

For broader product direction, use:
- [Today Screen Product Principles (Current)](/docs/product/today-screen-product-principles-current)
- [DayPlan Today Screen Decision Memo (Current)](/docs/product/dayplan-today-screen-decision-memo-current)

## Current Truth

The current LockedIn web Today page is already a real customizable workspace.

It is not just:
- a fixed dashboard
- a static homepage
- a hard-coded card stack

It already supports:
- persistent user layout
- drag and drop reordering
- widget resizing
- hide / restore behavior
- add-widget behavior
- shape-adaptive widgets that materially change presentation based on available space

The underlying concept is strong:

DormWay is giving students a modular academic workspace they can shape around how they actually work.

## The Main Product Problem

Most users likely do not understand that this customization exists.

That is not because the architecture is missing. It is because the interaction model hides the capability behind behaviors that are easy to miss or easy to misread:

- long press is not obvious
- long press only works on non-interactive background areas
- resize affordances do not read clearly as resize affordances
- the page looks more fixed than customizable when first viewed
- widget value changes by size are real, but the system does not explain that clearly

So the current gap is:

**the capability is stronger than the user understanding of the capability**

## What Is Working

### 1. The architecture is real

The current page is not faking customization. Save/cancel semantics, persisted layout, hidden widgets, and toolbar-based add behavior all make this a legitimate personalization system.

### 2. Widget reshaping is the right idea

The strongest architectural idea on the page is that widgets are not just stretched. They try to reinterpret themselves based on space. That is the right direction for a student workspace because different students will want different hierarchy:

- schedule-first
- tasks-first
- notes-heavy
- course-oriented
- compact vs. expanded

### 3. Default + customization is the right overall model

DormWay should not force students to build a dashboard before getting value. The default layout matters most. But students who care should be able to adapt the page to how they think. The current architecture supports that.

## What Is Not Working

### 1. Edit mode is too hidden

Long press on the page background is not a clear or teachable mental model for most users on desktop web. It is also easy to fail because the gesture does not work cleanly on interactive widget content.

Result:
- users may never discover customization
- users may think the page is static
- users may accidentally conclude DormWay is less flexible than it actually is

### 2. The entry condition is too fragile

Because long press must happen on non-interactive background, the user has to find dead space rather than just "holding down on Today." That is an important mismatch between:

- the intended product concept
- the actual interaction behavior

### 3. Resize handles are not legible enough

The corner-only resize handles currently read more like inconsistent blue dots than like purposeful grab handles. If users do not recognize them as resize affordances, the customization system loses a major part of its value.

### 4. Corner-only resizing feels constrained

Users expect larger surfaces to resize from edges as well as corners. Restricting resizing to corners only is making the system feel less direct than the underlying architecture actually is.

### 5. Value by size still needs clearer rules

The widgets do reshape, which is good. But the page still needs stronger product decisions about what each widget is best at in:

- compact state
- medium state
- large state
- wide vs. tall state

Without those rules, customization can expose weak states where a widget technically fits but is not especially useful.

## Product Interpretation

There are really two separate product questions:

1. Is the current default layout the best default?
2. Is the customizable widget architecture the right foundation?

Those should not be conflated.

Current answer:
- the architecture is promising and meaningfully real
- the discoverability and affordance layer is weaker than the architecture underneath it

That means the next work should focus less on reinventing the whole page and more on making the existing power legible.

## Immediate Recommendations

### 1. Make customization explicit from the default screen

Customization should be visible without requiring prior knowledge.

Current recommendation:
- keep the visible `Edit layout` control
- make it more prominent and more clearly tied to personalization
- use language closer to user intent, such as "Customize Today" if that tests better
- make the page feel like a customizable workspace from the start, not a static dashboard with a hidden trick

### 2. Reduce dependence on long press as the primary discovery path

Long press can remain as a shortcut, but it should not be the main discoverability mechanism on desktop web.

Better current role for long press:
- power-user shortcut
- secondary path

Not:
- the main way a student learns the page is customizable

### 3. Redesign resize affordances

The current resize handles need to look unmistakably interactive.

Immediate direction:
- make the handles read as handles, not dots
- consider larger corner affordances and visible edge affordances
- optimize for "I instantly understand I can resize this"

### 4. Define supported widget states more intentionally

Every widget should have a clear product contract by size:

- minimum useful size
- best compact use
- best expanded use
- what content should disappear, collapse, or simplify when space shrinks

This should be deliberate, not just whatever fits.

### 5. Make the promise of personalization clearer

The product should communicate that Today is:
- useful immediately by default
- customizable if you want it to be

That message matters because DormWay's value is partly in adapting to different students without demanding setup before first value.

## Near-Term Implementation Priorities

In order:

1. Improve edit-mode discoverability from the default screen
2. Improve resize handle legibility and interaction quality
3. Tighten widget value contracts across small / medium / large states
4. Re-evaluate whether background-only long press should remain, or whether it should become a secondary shortcut only

## What Not To Do

- Do not turn Today into a blank canvas that requires setup before value
- Do not rely on hidden gestures as the main explanation of customization
- Do not add more widget complexity before the existing customization model is legible
- Do not confuse criticism of the default layout with criticism of the modular architecture

## Bottom Line

The current LockedIn web Today page already has a stronger customization system than most users will realize on first use.

The problem is not that the concept is absent. The problem is that the concept is hidden.

So the next highest-value work is not inventing a new architecture. It is making the current architecture understandable, usable, and obviously customizable from the moment a student lands on Today.
