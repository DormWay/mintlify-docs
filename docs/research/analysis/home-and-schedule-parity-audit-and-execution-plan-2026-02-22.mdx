## Timezone Product Rule (Locked)

Order of precedence for schedule day boundaries and time labels:
1. User schedule preference timezone (if set)
2. Campus timezone (if available)
3. Account metadata timezone
4. Device local timezone (last fallback only)

Implementation constraints:
- [confirmed in code] Backend already resolves display timezone in key schedule endpoints:
  - `/Users/rileycrimmins/DormWay/dormway-beta-workspace/.repos/dormway-platform/services/api-router/src/routes/v2/students.routes.ts:6621`
- [inferred] iOS should consume a resolved timezone context rather than ad hoc `TimeZone.current` in service formatters.

Required test coverage:
- DST boundary week
- travel scenario (device timezone differs from campus)
- midnight boundary for due items/events

## Validation Plan (Usability)

1. Rushing to class
   - Task: open app and locate next class destination.
   - Success: <=5s, >=90% success.

2. Between classes
   - Task: identify and start next best task.
   - Success: <=8s, >=85% success.

3. Late-night catch-up
   - Task: produce realistic tonight plan from backlog.
   - Success: <=60s planning time, >=80% confidence.

4. Exam week overload
   - Task: identify top 3 risk items this week.
   - Success: >=85% agreement with backend truth.

5. Weekend reset
   - Task: prepare next week with at least two planned work blocks.
   - Success: <=3 minutes, >=80% completion.

6. Panic check
   - Task: answer “what am I missing right now?”.
   - Success: no hidden overdue critical items.
