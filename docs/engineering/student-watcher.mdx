# StudentWatcher Workflow

StudentWatcher is DormWay's per-student Temporal workflow and still the main owner of student state. The current April 2026 direction is more precise than the old "watcher does everything" model: StudentWatcher should own state, signals, and plan regeneration, while timer-heavy delivery work gradually moves into dedicated routers.

## Overview

| Property | Value |
|----------|-------|
| Workflow name | `studentWatcherWorkflow` |
| Task queue | `student-worker` |
| Workflow ID pattern | `student-watcher-${studentId}` |
| Source file | `services/engine/src/workflows/studentWatcher.simplified.workflow.ts` |

The workflow starts during onboarding or signup flows and rolls forward with `continueAsNew` to keep Temporal history manageable.

## Current Responsibility Boundary

The important current split is:

- **StudentWatcher owns** student state, signal handling, preference changes, DayPlan regeneration, and sync-trigger fan-in
- **Routers are starting to own** due-intent delivery work like scheduled DayPlan sends

That is the architecture to preserve when adding new work.

## Phase 1A Changes That Landed

The April 16 watcher work changed a few major runtime behaviors:

- replay-safe smart sleep using `condition()` for new histories instead of a fixed 1-minute loop
- dedicated wake-time helpers in `studentWatcherWakeTime.ts`
- signal wake flags so real signals wake the workflow immediately
- startup dayplan recovery so pending scheduled actions survive restarts
- lightweight Canvas connection-status caching in workflow state
- time-based hourly checks replacing older modulo-style timing gates in the new path

The relevant patch markers introduced in this phase are:

- `studentwatcher-condition-smart-sleep-v1`
- `studentwatcher-startup-dayplan-recovery-v1`

## Router Handoff

StudentWatcher is no longer the only place timed DayPlan work can live.

The current routed-delivery path uses:

- durable `engine_delivery_intents` rows
- a global `dayPlanRouter.workflow.ts`
- a handoff feature flag: `feature.dayplan_router_enabled`

When that path is enabled, scheduled DayPlan push delivery can be claimed and sent by the router instead of waking StudentWatcher just to proxy the send.

## Start Points

- signup and onboarding flows can start it
- admin routes can signal it
- city-level sync jobs can fan out signals to relevant student workflows

## Persisted State

- `student_watcher_state` stores the workflow's durable state snapshots
- workflow status queries expose current plan and generation metadata

## Known Risk

Any new timed feature that defaults into the watch loop works against the current direction. If the work is really "claim due item and send it," it probably belongs in a routed delivery path rather than in StudentWatcher itself.
