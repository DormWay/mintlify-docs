# Task Bank Canonicalization Spec (Draft)

## Summary
Unify every task surface (Schedule work queue, Tasks page, Today widgets, mobile) behind a canonical task identity and a deduped, server-side Task Bank response. The goal is to eliminate duplicate items, prevent timezone drift in due dates, and make Task Bank a stable, reliable source for Smart Schedule.

## Goals
- Single canonical task identity across sources (Tasks table, Canvas, syllabus/ICS, DayPlan, quick captures).
- Server-side dedupe so all clients see the same list and counts.
- Stable due-date handling (date-only vs time-specific) consistent with display timezone.
- Clear source precedence and merging rules.
- Backward compatible API responses.

## Non-Goals
- UI redesigns outside Task Bank surfaces.
- Rewriting the DayPlan generator logic.
- Changing Canvas sync mechanics.
- Removing legacy endpoints in this phase.

## Current State (Problems)
- Task Bank merges DayPlan + Canvas + captures + persistent tasks with only a limited dedupe rule (`metadata.originalId`).
- Clients are forced to implement their own dedupe; behavior differs by surface.
- Due dates for date-only tasks can drift when timezone conversions happen twice.
- Duplicate assignment tasks appear with different title formatting (prefix vs bracketed course code).

## Desired Behavior
- Task Bank returns a canonical list with no duplicates.
- Clients render the task list without additional dedupe logic.
- Each task item includes `canonical_id`, `canonical_key`, and `sources[]`.
- Date-only tasks render as end-of-day in the user display timezone (not 7pm drift).
- `/v2/students/me/task-bank` and `/api/mobile/planner/task-bank` share the same canonicalization logic so counts match across surfaces.

## Data Model Changes
### tasks table (existing)
Add or backfill:
- `canonical_key` (string, indexed)
- `source_type` (enum or string)
- `source_id` (string)
- `source_priority` (integer)

### canonical id (API only in Phase 1)
- If a `tasks` row is present in the merged group, use `tasks.id`.
- Otherwise, use a deterministic hash of the canonical key: `canon_<sha1(canonical_key)>`.

### canonical key
```
{normalized_title}|{normalized_course}|{due_day_local}
```
Normalization rules:
- Strip course codes from title when course is known.
- Normalize course codes to `SUBJ 123` format.
- Use user display timezone to compute `due_day_local`.

### canonical key details (Phase 1)
```
canonical_key = {title_key}|{course_key}|{due_key}
```
- `title_key`: lowercase, trim, collapse whitespace, remove common course prefixes like `SUBJ 101 -` or `[SUBJ 101]`.
- `course_key`: prefer `courseContextId`; else normalized course code; else `none`.
- `due_key`:
  - If time-specific: `YYYY-MM-DDTHH:mm` in display timezone.
  - If date-only: `YYYY-MM-DD` in display timezone.
  - If missing: `none`.
- `has_time`: `true` when the source provides a time component (not all-day); otherwise `false`.

### source identity mapping (Phase 1)
- `tasks`: `source_id = tasks.id`; if `metadata.canvasAssignmentId` exists, also include `source_type=canvas` in `sources[]`.
- `canvas`: `source_id = canvas_assignments.id`.
- `dayplan`: `source_id = dayplan block id`.
- `quick_capture`: `source_id = service_data.id`.
- If `metadata.originalId` exists on a persistent task, include it as an additional `source_id` entry for dedupe.

### current source values (for normalization)
- `tasks` table rows use `source` = `manual` | `assignment` | `dayplan` | `ai_suggestion`.
- Task Bank aggregation currently labels quick captures as `capture` and Canvas assignments as `canvas`.
- Normalize these into canonical `source_type` values; keep the original `source` in the task payload unchanged for backward compatibility.

### dedupe algorithm (Phase 1)
0. Normalize `source_type` values to canonical labels: `tasks`, `canvas`, `syllabus`, `ics`, `dayplan`, `quick_capture`.
1. Group by `source_type:source_id` when both are present.
2. For remaining items, group by `canonical_key`.
3. Guardrails:
   - If `course_key=none` and `due_key=none`, only merge when `source_type:source_id` matches.
   - If `course_key=none`, do not merge across different `source_type` values unless one source explicitly references the other (ex: `tasks.source_id` matches a Canvas assignment id).

## API Contract Changes
### GET /v2/students/me/task-bank
Add fields (backward compatible):
- `canonical_id` (string)
- `canonical_key` (string)
- `sources` (array of { source_type, source_id, priority })
- `has_time` (boolean | null)
- `due_date` (YYYY-MM-DD | null)

Dedup behavior:
- Prefer persistent tasks over Canvas over syllabus/ICS over DayPlan over captures.
- Merge metadata across sources; preserve all `source_id` values.

### GET /api/mobile/planner/task-bank
- Keep response shape stable, but apply the same dedupe and canonicalization logic.
- Optional: include `canonical_id`, `canonical_key`, `sources`, `has_time`, `due_date` fields for parity (clients can ignore).

### GET /v2/students/me/tasks
No contract change required in phase 1, but share canonical key generation with task-bank.

## Source Precedence (initial)
1) `tasks` (manual or assignment-backed)
2) `canvas` assignments
3) `syllabus` / `ics` assignment deadlines
4) `dayplan` suggestions
5) `quick_capture`

When duplicates collide:
- Keep the highest-priority task as the primary.
- If priority ties, pick the item with `has_time=true`, then the earliest `due_at`, then stable sort by `source_type:source_id`.
- Merge `course`, `due`, and `estimatedMinutes` if missing in primary.
- Prefer time-specific `due_at` over date-only when both exist.
- Combine `sources[]`.

## Client Responsibilities
- Render Task Bank using `canonical_id` and ignore duplicates.
- Show due dates using `due_date` + `has_time` from the API.
- Keep existing fallbacks for older API responses until rollout completes.

### Canonicalization Helper (Phase 1)
Proposed helper signature (api-router):
```
type CanonicalSource =
  | 'tasks'
  | 'canvas'
  | 'syllabus'
  | 'ics'
  | 'dayplan'
  | 'quick_capture';

type CanonicalSourceRef = {
  source_type: CanonicalSource;
  source_id: string;
  priority: number;
};

type CanonicalTask = {
  canonical_id: string;
  canonical_key: string;
  sources: CanonicalSourceRef[];
  has_time: boolean | null;
  due_date: string | null; // YYYY-MM-DD
  primary: UnscheduledTask; // original task shape used by endpoint
};

function canonicalizeTaskBank({
  tasks,
  displayTimezone,
  sourcePriority,
}: {
  tasks: UnscheduledTask[];
  displayTimezone: string;
  sourcePriority: Record<CanonicalSource, number>;
}): {
  items: UnscheduledTask[];
  canonical: CanonicalTask[];
  metrics: {
    rawCount: number;
    dedupedCount: number;
    dedupedBySourceId: number;
    dedupedByKey: number;
    sources: Record<CanonicalSource, number>;
  };
};
```

## Metrics
- Task Bank duplicate rate (raw_count vs deduped_count).
- Client-side dedupe usage (should drop to zero).

## Risks
- Mismatched course codes across sources can still create duplicates if normalization is insufficient.
- Canvas assignments without course codes may merge incorrectly.
- Backfilling tasks could shift existing IDs used by clients.

## Open Questions
- Should we expose `canonical_id` in other APIs (dashboard widgets, Today widgets)?
- Do we want a dedicated Task Bank table or compute in-memory on request?
- Should DayPlan store references to canonical tasks or continue as suggestions?

## Definition of Done
- Task Bank responses contain canonical IDs and no duplicates for known test accounts.
- Schedule work queue, Tasks page, and Today widgets show identical counts for the same user.
- Date-only tasks render at end-of-day in display timezone with no 7pm drift.
