## What Already Exists (Strong Alignment)

- **DayPlan V2** is production and already central to daily intelligence. It provides daily priorities and hard commitments but is day-scoped. [DayPlan V2](/docs/engineering/architecture/sot-dayplan-v2)
- **Schedule processing** already reconciles multiple calendar sources into `student_time_blocks`, which is the canonical schedule for the UI and for DayPlan input. [Schedule Sources & Precedence (Current)](/docs/engineering/technical/calendar/schedule-sources-precedence-current)
- **Syllabus extraction** produces structured data and stores it in service_data, which can be used for session prep mappings. [Syllabus Processor Deployment Plan - August 2025](/docs/engineering/technical/migration-deployment/syllabus-processor-deployment-plan-august-2025)
- **Canvas assignments** already flow into `student_time_blocks`, so assignments are already present in the core schedule data used by DayPlan. Engineering/Technical/API/Canvas/Canvas Integration Alignment Plan

---

## Partially Aligned (Exists but Not Wired End-to-End)

- **Announcements**: a `fetchCanvasAnnouncements` activity exists, and the canary workflow detects announcement changes, but announcements are not persisted as session-level data or surfaced in schedule detail views.
- **Canvas meeting times**: Canvas is treated as a high-fidelity source, but meeting times are not projected to `time_blocks` yet, so class schedule still depends on imports/ICS/manual sources.
- **DayPlan enrichment with Canvas**: DayPlan is powered by `student_time_blocks`, but does not join Canvas tables directly, and does not generate session-specific prep actions. [Canvas to DayPlan Integration Plan](/docs/engineering/technical/api/canvas/canvas-to-dayplan-integration-plan)

---

## Net-New Work Required for Event Readiness

- **SessionPlan cache**: a per-session representation of required prep items and logistics.
- **Mapping layer**: deterministic rules + light LLM support to attach syllabus/LMS requirements to specific class meetings.
- **Announcement ingest & attachment**: persist announcements and map them to sessions with location/cancellation keywords.
- **Confidence + provenance model**: every item should carry source + timestamp + confidence.
- **Schedule detail UI**: session prep card with action links and completion toggles.

---

## Key Constraints & Sharp Edges

- **Schedule reconciliation can delete sources it didn’t ingest.** If a data source is not included in `scheduleProcessor` inputs, it can be deleted from `student_time_blocks`. This is relevant for Canvas assignment rows and any future session prep projections. [Schedule Sources & Precedence (Current)](/docs/engineering/technical/calendar/schedule-sources-precedence-current)
- **DayPlan only consumes `student_time_blocks`.** Any new prep intelligence must either land in that table or be joined explicitly during DayPlan generation. [DayPlan V2 Architecture](/docs/engineering/architecture/dayplan-v2-architecture)
- **Model configuration drift.** The SoT references Gemini 2.5 Flash Lite, while the DayPlan V2 architecture doc references GPT-4o-mini. This should be reconciled to avoid confusion in future changes. [DayPlan V2](/docs/engineering/architecture/sot-dayplan-v2), [DayPlan V2 Architecture](/docs/engineering/architecture/dayplan-v2-architecture)

---

## Implications for Rollout

- **Phase 0 prerequisite:** ensure Canvas announcements are persisted and queryable.
- **Phase 1 prerequisite:** session prep mapping should run in a batch job (per course/week) to avoid per-event LLM costs.
- **Phase 2 prerequisite:** update schedule detail UI to consume a session prep payload (cached).
- **Risk:** without announcement coverage, the most critical session updates (cancellations/room changes) will be missing and trust will erode.
