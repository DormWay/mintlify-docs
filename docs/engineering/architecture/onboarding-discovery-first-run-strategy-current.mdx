# Onboarding Discovery & First-Run Strategy (Current)

## Summary
DormWay should move first-run onboarding from instruction-heavy flows to discovery-first guidance that lives inside the Today surface. The intent is to reduce pop-up fatigue, keep the user in context, and teach key behaviors through real actions (create a task, plan a block, customize the dashboard) rather than a click-next tour.

This doc describes the intended path forward, why it is the right fit for Gen Z students, and the concrete implementation plan with code references.

## Goals
- Help new users achieve a first success (schedule or plan something) within minutes.
- Replace generic tours with in-context hints and task-driven learning.
- Keep the Today surface as the primary "zoom-out" hub for discovery.
- Make first-run guidance feel optional, helpful, and short-lived.

## Non-goals
- Do not add another full-screen click-next tutorial.
- Do not block core usage with required modals beyond the existing profile onboarding.
- Do not persist fake tasks into the database as real records.

## Why This Strategy (Reasoning)
- Gen Z students respond better to discovery and action than forced instruction.
- The Today surface is already the hub for planning, widgets, and status. Onboarding should live there.
- Contextual hints are lower friction and respect user autonomy.
- Dummy or ghost data solves empty-state anxiety without polluting real data.
- Task-driven learning is sticky: "Do a thing" beats "Read about a thing".

## Strategy Overview
We will build a layered, discovery-first system that is mostly passive:

1) Contextual hint layer (persistent but subtle)
2) First-run ghost data (not saved to DB)
3) Just-in-time tooltips (intent-triggered)
4) Today checklist expansion (progress-driven, optional)
5) Optional micro-tips (short clips) in a secondary location

## Phased Implementation Plan

### Phase 0 - Baseline instrumentation and gating
- Confirm existing events in `services/dormway-lockedin/src/types/amplitude-events.ts` and add new ones:
  - `discovery_hint_shown`, `discovery_hint_dismissed`, `discovery_hint_clicked`
  - `ghost_task_clicked`, `ghost_task_converted`
  - `first_plan_created`, `first_task_created`
- Decide gating state storage:
  - Short-term: localStorage keys (mirrors current edit hint behavior)
  - Long-term: preferences API (`/v2/students/me/preferences`) for cross-device consistency

### Phase 1 - Discovery Hint component
- Build a reusable `DiscoveryHint` wrapper on top of the existing `Hint` overlay.
- Add a pulse/halo indicator that is time-boxed (auto stops after N seconds or on interaction).
- Each hint should be "show once" with a unique key.
- Initial placements (high-confusion surfaces):
  - Today "Edit layout" entry points
  - Week Planner grid / Right rail details
  - Primary "Plan" action (where it exists)

References:
- `services/dormway-lockedin/src/components/ui/overlay-system/hint.tsx`
- `services/dormway-lockedin/src/app/dashboard/today/page.tsx`
- `services/dormway-lockedin/src/app/dashboard/schedule/page.tsx`

### Phase 2 - First-run ghost data (no DB writes)
- Inject 2-3 ghost tasks into the tasks data for new users only.
- Ghost tasks are clearly labeled (ex: "Try planning a study block").
- Clicking a ghost task should open the real planner and convert to a real task only if the user confirms.
- Use metadata flags (already supported in dashboard types) to mark placeholders:
  - `metadata.isPlaceholder = true`
  - `metadata.placeholderType = "quickstart" | "tutorial"`

References:
- `services/dormway-lockedin/src/hooks/home/useDashboardComposite.ts`
- `services/dormway-lockedin/src/components/ui/academic/TaskRow.tsx`
- `services/dormway-lockedin/src/app/dashboard/today/widgets/*`

### Phase 3 - Just-in-time tooltips
- Add intent-based tooltips for high-ambiguity controls (ex: weather icon, month bars).
- Trigger on hover dwell (desktop) or long-press (mobile).
- Use existing overlay system; avoid persistent tooltip stacks.

References:
- `services/dormway-lockedin/src/components/ui/overlay-system/hint.tsx`
- `services/dormway-lockedin/src/lib/z-index.ts` (tooltip z-index)

### Phase 4 - Expand the Today checklist
- Extend SetupWidget to include 1-2 task/plan milestones:
  - "Create your first task"
  - "Plan your first block"
- Auto-complete milestones based on real behavior (not clicks).
- Keep SetupWidget dismissible and collapsed by default once completed.

References:
- `services/dormway-lockedin/src/components/dashboard/SetupWidget.tsx`
- `services/dormway-lockedin/src/app/dashboard/today/page.tsx`

### Phase 5 - Optional micro-tips
- Add a small "Quick Tips" section in the SetupWidget footer or a help drawer.
- Short clips (10-15s) showing key actions.
- Only shown on request; never auto-play or auto-open.

## UI and Behavior Principles (Do/Do Not)
- Do: prefer subtle hints and optional guidance.
- Do: keep guidance context-aware and time-limited.
- Do: use ghost data for empty-state relief.
- Do not: introduce another blocking tutorial or forced modal.
- Do not: auto-persist fake tasks or schedules to the database.

## Concrete Deliverables (for agents)
- `DiscoveryHint` component that wraps `Hint` and supports:
  - `id` key, `showOnce`, `pulse`, `openDelay`, `maxSessions`
- A `useDiscoveryHints` hook to manage localStorage gating and event tracking.
- Ghost task injection in the Today/task widget data pipeline.
- SetupWidget task expansion and completion rules.

## Acceptance Criteria
- New users can reach "first task planned" without encountering a modal tutorial.
- Hint impressions are under a capped threshold per session (avoid fatigue).
- Ghost tasks disappear once a real task exists or the user dismisses them.
- SetupWidget completion rate improves without reducing retention.

## Risks and Mitigations
- Risk: too many hints create visual noise.
  - Mitigation: strict caps per session and per surface.
- Risk: ghost data confuses users.
  - Mitigation: label clearly and convert only on explicit action.
- Risk: duplication between onboarding and first-run.
  - Mitigation: keep `/onboarding` profile-only; keep discovery on Today.

## Open Questions
- Which surfaces are most confusing today: Week Planner, Right Rail, or Tasks?
- Should hint state be stored per device (localStorage) or account (preferences)?
- Is there a single "first success" metric we want to optimize (ex: first plan vs first upload)?
