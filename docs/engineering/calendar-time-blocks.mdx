# Calendar and Time Blocks

DormWay's calendar stack has three separate concerns:

1. inbound calendar normalization and storage
2. student-facing time block queries
3. outbound subscription feeds and academic calendar enrichment

## Storage Model

| Table | Role |
|-------|------|
| `time_blocks` | Generic normalized event store |
| `student_time_blocks` | Student-facing blocks used by most app surfaces |

Important current-state note: `student_time_blocks` is a base table in production Neon, not just a clean view alias. Any deletion or repair logic that assumes a view will be incomplete.

## Inbound Sources

- LMS ICS feeds like Canvas and Moodle
- Google calendar credentials and sync jobs
- manual and schedule-import sources
- syllabus and academic-calendar derived events

Normalization happens before storage, with course-code reconciliation and lifecycle filtering layered on top.

## Outbound Subscription Feeds

Students can subscribe to a personal ICS feed backed by `student_time_blocks`.

- token generation is HMAC-based
- the raw token is not stored directly
- the public feed route must stay explicitly public in Zuplo
- DormWay-origin ICS exports mark events so they are not re-imported back into the system

## Academic Calendar

Campus term dates, breaks, and exam periods are canonically stored in `service_data` under campus enrichment methods, with `campus_configs.academic_calendar` acting as the performance cache.

## Timezone and DST Rules

This is the most important implementation constraint in the calendar system.

| Operation | Wrong | Correct |
|-----------|-------|---------|
| Store local time as UTC | `new Date(local).toISOString()` | `fromZonedTime(local, timezone).toISOString()` |
| Render UTC for a user | `new Date(utc).toLocaleString()` | `formatInTimeZone(parseISO(utc), timezone, format)` |
| Parse stored ISO time | bare `new Date()` everywhere | `parseISO()` plus timezone-aware formatting |

<Warning>
  Do not use bare `new Date()` logic for schedule display or local-time-to-UTC conversion on DST boundaries. The canonical approach is `date-fns-tz` with the stored IANA timezone.
</Warning>
