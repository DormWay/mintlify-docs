# DayPlan V2

DayPlan is DormWay's daily intelligence artifact. V2 is the current production path and is centered on a priority-first daily brief instead of a minute-by-minute scheduler.

## Core Facts

| Property | Current contract |
|----------|------------------|
| generation time | 5 AM user local time |
| storage | `service_data` with method `dayplan` |
| trigger owner | StudentWatcher |
| downstream effects | feed generation, delivery intents, briefings, client refreshes |

## V2 Output Shape

The important V2 fields are:

- `dueToday`
- `hardCommitments`
- `conflicts`
- `suggestedBlocks`
- `nearFuture`
- `summary`
- `notificationContent`
- `currentState`
- `actions`

Older timeline fields still exist for compatibility, but V2's product meaning comes from the priority-first fields above.

## Generation Flow

1. StudentWatcher decides a new day plan is needed
2. generation activities pull current data and prior-state context
3. the plan prompt is built with anti-hallucination rules
4. the model returns the structured plan
5. the plan is stored and can trigger feed regeneration and outbound delivery work

## Delivery Architecture

The key April 2026 change is that DayPlan delivery is no longer treated as a single watcher-owned concern.

Current shape:

- DayPlan generation still happens from the watcher path
- a deterministic DayPlan-to-intent builder writes durable `engine_delivery_intents`
- stale intents are superseded when a newer plan replaces the old one
- `DayPlanRouter` can claim due intents and send them directly when the feature flag is on

## Important Contracts

- generation is timezone-aware
- `currentState` updates separately from full plan generation
- downstream systems should not treat every state touch as a full plan refresh
- Ace can reference DayPlan as context, but Ace does not own schedule recommendations
- quiet hours, preference gates, and superseded-plan checks still apply before delivery

## Current Reliability Notes

Recent DayPlan work surfaced a few important truths:

- duplicate morning emails were traced to insufficient watcher-side resend guards on fresh runs
- prompt and schema logic in `dayplan.activities.ts` is powerful but still complex enough that auditability matters
- the router migration is meant to reduce timing and delivery complexity without changing the student-facing meaning of the DayPlan itself
