## What `/dev/brandbook` Encodes Today

### 1) Structure of the brandbook page
The page is built as an implementation playbook with explicit chapters:
1. Positioning
2. Message framework
3. Identity
4. Color system
5. Typography
6. Product signature
7. Motion
8. Voice
9. Accessibility
10. Dev implementation rules
11. Governance

This is not just visual inspiration; it encodes practical release checks and implementation constraints.

### 2) Token-first styling model
The page uses design-system variables (`--ds-*` and `--theme-*`) as first-class inputs and audits live computed token values for contrast checks.

Core signals:
1. Foundation + semantic tokens (`--ds-primary-brand`, `--ds-surface-*`, `--ds-text-*`, `--ds-success|warning|error|info`).
2. Theme parity rails for `light`, `dark`, `glass`.
3. Token usage guardrail: production routes should avoid hard-coded colors.

### 3) OS concept mode behavior
The page supports an “OS concept” overlay mode:
1. Mesh background (`/public/brandbook/os-mesh.svg`).
2. Floating launcher (`Cmd/Ctrl + K`) and rail icon interactions.
3. Local CSS variable overrides for card/floating surfaces and motion.

Important current behavior note:
- `src/lib/osConcept.ts` currently forces concept mode enabled in storage helpers (always writes/returns enabled behavior). Treat this as implementation reality when debugging toggles.

### 4) Motion and interaction system
Motion guidance is explicit:
1. Hover/press: ~120-180ms.
2. Panel entry: ~220-280ms.
3. Ambient effects constrained and reduced-motion aware.

Implementation details include:
1. `data-lift` hover elevation patterns.
2. Reduced-motion hard fallbacks.
3. Keyboard close/open patterns for launcher and overlays.

### 5) Accessibility + release gates built into the page
The page includes concrete gates:
1. WCAG AA contrast checks (4.5:1 target).
2. Visible focus ring requirement.
3. No color-only critical state signaling.
4. Theme parity verification.
5. Desktop + mobile screenshot expectations.

## Styling Rules for Future Coding
Use these as practical coding rules:
1. Keep surfaces neutral-first; accents are selective and purposeful.
2. Use one dominant accent per viewport.
3. Reserve strong glass/gradient treatment for hero, overlay, or trust moments.
4. In dense productivity workflows, prefer clear surface stacks over decorative glow.
5. Every panel should expose one clear next action with explicit verb labels.

## iOS Alignment Plan (Required)

### iOS should align on semantics, not copy web layout mechanics
Do align:
1. Color/semantic token intent (brand primary, semantic states, surface hierarchy).
2. Accessibility and release gates (contrast, reduced motion/transparency, keyboard/focus where relevant).
3. Messaging posture in UI copy (direct, calm, actionable).

Do not force:
1. Web nav rail/brandbook shell patterns onto iPhone/iPad production flows.
2. Desktop density patterns into touch-first surfaces.

### Current iOS alignment status
1. Brand primary alignment exists in iOS design tokens (`#6366F1` family present in `DWDesign` token sources and generated DS color surfaces).
2. iOS has a mature glass stack (materials + layered modifiers + shader support paths) documented in `LIQUID_GLASS_IMPLEMENTATION.md`.
3. iOS already has adaptive material abstractions; continue using them rather than ad hoc per-view styling.

### iOS implementation checklist for parity with brandbook intent
1. Ensure DormWay primary remains token-driven and consistent with web brand primary intent.
2. Keep semantic color meaning stable (`success`, `warning`, `error`, `info`) across app surfaces.
3. Apply glass effects where they improve hierarchy/context, not on every dense workflow card.
4. Validate contrast and reduced-motion/reduced-transparency behavior before release.
5. Keep typography hierarchy explicit: display/section/body/utility.
6. Document any foundational token changes in both web brandbook docs and iOS design-system docs.
