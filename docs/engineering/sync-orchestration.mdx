# Sync Orchestration

DormWay uses Temporal schedules plus orchestration endpoints to keep city, campus, calendar, and course data fresh without pushing scheduling complexity into clients.

## Schedule Provisioning

Schedule provisioning only happens when `SYNC_SCHEDULES_ENABLED === 'true'` during engine boot.

Current core schedules:

- `sync-hourly-smart`
- `sync-city-4h`
- `sync-daily-force`
- `sync-term-data-enrichment`
- cleanup schedules
- `plugin-runner-5m`

All of these use skip-style overlap behavior so a backlog does not explode into duplicate runs.

As of the April 2026 optimization work, it is also important to separate **schedule provisioning** from **due-intent delivery**. The orchestration layer still owns recurring city/campus/account jobs, while routed DayPlan delivery is starting to move into its own workflow path.

## Orchestration Flow

1. Temporal schedule triggers a workflow bridge
2. The bridge calls the API router orchestration endpoint
3. The orchestration service selects candidates
4. City or campus workflows start with idempotent IDs
5. Results eventually land in canonical stores like `service_data`

## Student-Level Runtime Split

The old mental model was "StudentWatcher owns basically all timed student work." The current model is more specific:

- orchestration schedules still trigger city, campus, and other recurring system jobs
- StudentWatcher still owns per-student state and sync-trigger fan-in
- `DayPlanRouter` now owns the first dedicated batch claim/send path for due DayPlan intents

## Dedupe Rules

- city workflows: `city-sync-${contextId}`
- campus workflows: `campus-sync-${contextId}`
- calendar-triggered workflows use sharded and bucketed IDs
- account-level calendar sync also uses dedupe windows to suppress burst fan-out
- delivery intents are deduped and superseded separately from orchestration schedules

## Schedule Import and Removal

| Workflow | Responsibility |
|----------|----------------|
| `scheduleImport.workflow.ts` | Normalize imported schedule data into `time_blocks` |
| `scheduleRemoval.workflow.ts` | Clean dropped-course data out of `time_blocks` and `student_time_blocks` |

This is important because student-facing schedule cleanup cannot assume `student_time_blocks` is a derived-only view.
