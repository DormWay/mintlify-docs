# Auth and Identity

DormWay auth is multi-surface, not single-provider. Web traffic usually arrives through Zuplo with Clerk JWTs, mobile uses device-key based identity, and system flows still include Auth0 action routes plus internal, cron, and Temporal credentials.

## Canonical Auth Order

Core auth resolves credentials in this order:

- internal API key
- Temporal worker key
- device key
- Clerk JWT
- API gateway `x-user-*` headers
- direct JWT verification

That ordering lives in the shared auth factory and is the contract other middleware builds on.

## Surface Matrix

| Surface | Primary credential | Important contract |
|---------|--------------------|--------------------|
| LockedIn / Admin web | Clerk JWT | Usually validated at Zuplo, then forwarded via user headers |
| iOS app | Device key | Resolved into a backend user before api-router handlers run |
| Auth0 actions | `SYSTEM_API_KEY` + `x-auth0-action` | Used for system provisioning and claim context routes |
| Cron / internal routes | API key headers | Must match cron/system middleware expectations |
| App-auth flows | HMAC headers | `x-app-signature` and `x-app-timestamp` gate app-integrity style requests |

## Provisioning Flows

### Clerk signup webhook

`POST /api/webhooks/clerk` creates the account, links student context, and starts StudentWatcher. Signup should succeed even if the workflow start is logged as a non-blocking failure.

### Auth0 system routes

Auth0 is not the primary end-user web auth path anymore, but it is still part of the provisioning and claims surface. The important system routes require `SYSTEM_API_KEY` and an allowed `x-auth0-action` value.

### Magic link resend

`POST /api/v2/auth/resend-magic-link` goes through Clerk plus Customer.io. This is part of the PLG auth path, not a separate legacy-only branch.

## Identity Model

- Backend user identity is the UUID that ultimately lands in `req.user.id`
- Clerk JWTs map `backend_user_id` first, then fall back to `sub`
- Accounts do not carry a canonical `campus_id` column; campus identity resolves through the context graph
- Guest flows still exist for crew participation and later account merge

## RLS and Database Access

| Connection | RLS | Usage |
|------------|-----|-------|
| `DATABASE_URL` | Enforced | User-scoped application reads |
| `DATABASE_URL_ADMIN` | Bypassed | System writes, migrations, admin operations |

`@dormway/core` relies on this split. If you debug with the user-scoped URL and do not set the expected RLS session, empty results are often the correct behavior.
