# Notifications and Customer.io

DormWay uses Customer.io as the main outbound system for visible push, transactional email, and activation lifecycle messaging. Customer.io does the sending, but DormWay still owns timing, deep-link correctness, trait truth, preference gating, and dedupe behavior.

## Core Responsibilities

- profile identification and trait updates through the shared adapter
- transactional email and push delivery
- preference-aware channel gating
- scheduled reminder and briefing delivery
- activation and recovery messaging after signup
- hybrid routing between direct push paths and Customer.io-backed flows

## Trait Contract

Traits that already exist and matter:

- `campus_id`
- `campus_name`
- academic profile fields like `academic_year` and `major`

Traits called out by the current activation docs:

- `first_action_completed`
- `first_action_date`
- `next_best_first_action`
- `first_action_type`

One of the important April findings was timing-related: the welcome campaign can render before some first-action traits are available if those traits are only written after activation.

## Common Notification Families

| Family | Typical source |
|--------|----------------|
| DayPlan push and email | StudentWatcher, DayPlan activities, and routed delivery intents |
| briefing and check-in sends | notification delivery activities |
| syllabus success or failure email | syllabus processing workflows |
| signup / activation recovery | onboarding flows plus Customer.io journeys |
| magic link resend | auth routes plus Customer.io |
| Canvas alerts | canvas activities |

## Welcome Campaign Reality

The current Welcome campaign is a reshape, not a greenfield build.

What matters operationally:

- the campaign already existed in Customer.io
- timing was reworked toward `0h / +1h / +24h / +48h`
- LMS-connect branching was added for Canvas and non-Canvas campuses
- several legacy CTA URLs were invalid and had to be corrected

### Canonical deep links

| Intent | URL |
|--------|-----|
| Syllabus upload | `/dashboard/library?openUpload=1` |
| Schedule import | `/dashboard/schedule?scheduleModal=import` |
| Canvas connect | `/dashboard/courses?tab=canvas` |
| Generic LMS connect | `/dashboard/settings?tab=connections` |

## Preference Gating

- quiet hours apply before sending visible notifications
- `dayplan.email_on_light_days` can suppress lighter-day emails
- per-type flags like class reminders and assignment deadlines must be respected
- push channel availability implies in-app availability in the shared delivery model

## Delivery Ownership

Customer.io is not the only runtime involved in notifications.

- engine activities still decide when a send should happen
- StudentWatcher still participates in message timing around DayPlan and sync-driven updates
- `DayPlanRouter` is now the first dedicated routed delivery path for due intents
- workflow logic, not Customer.io payload idempotency alone, is where DormWay handles dedupe and supersession semantics
